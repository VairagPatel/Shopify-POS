Existing-customer lookup and phone privacy are implemented changes. Customer registration and a full customer-ID-based clinical redesign are proposals. This guide labels the difference.

1. Customer lookup is not customer creation

The current “Add wearer” action adds an existing person to a bill. It does not create a new Shopify customer.

We now call POST /api/customers with a JSON body. This remains a lookup despite using POST: the phone is private request input, so it should not appear in a query string.

{
  "phone": "9000000005"
}
Enter phone→Normalize to +91→Find source customer→Read source + local Rx→Add wearer to bill

A missing source customer returns 404. The app does not invent a local customer or create a source account automatically. New-customer registration is described in chapter 6 as proposed work, as requested.

The previous GET /api/customers?phone=... contract is retired. It now returns 405. This is an intentional API compatibility change for privacy. Swagger, frontend lookup and automated callers were updated.

A schema describes fields, types and validation. An API is the action that accepts or returns those fields. A database table is where selected records are stored. They are related but not interchangeable.

2. One phone format everywhere

Rule: this demo accepts Indian mobile numbers only. Keep phone as a string, remove permitted formatting spaces/brackets/hyphens, recognize +91 / 91 / a leading domestic 0, then require ten digits beginning with 6–9. Store and compare the result as +91 plus those ten digits.

Reject missing values, numeric JSON values, letters, unsupported country codes, extra digits and non-ASCII digit lookalikes. We do not silently guess the country. Formatting is not proof that a phone belongs to the customer; no OTP verification is implemented.

Existing data is not silently rewritten

The supplied seed already uses canonical phones. Saved historical orders, invoices and quotes are retained. This change is not a database-wide migration. If imported/old clinical records contain multiple formats, a controlled backfill and duplicate review is still needed; do not bulk-merge customers by phone without checking identity.

Use customer IDs as long-term identity

A phone can change or be shared by a family. The source customer.id is a better long-term relationship key. The current exercise store-tool lookup is by phone; local clinical writes also retain customer_id. A production redesign should query/link prescriptions by customer ID and treat phone as a searchable contact field. That redesign is proposed, not implemented here.

3. Phone privacy: browser, adapter and logs

Changed in this project
  • Browser lookup uses POST JSON, no phone query parameter.
  • Standard runner enables body-based customer and prescription lookup extensions.
  • No automatic fallback to a phone-in-URL lookup.
  • Standard Uvicorn access logging strips query strings.
  • Durable mock wrapper logs only the request path, not query values.
Still requires care
  • POST is not encryption. Use HTTPS for deployed traffic.
  • Authorized users can inspect request/response bodies in browser tools.
  • Phone still exists in clinical/quote/source data, receipts, draft storage and permitted responses.
  • Proxy, tracing, error and analytics systems need their own redaction rules.
  • Bootstrap still returns the synthetic customer directory; production should minimize bulk exposure.

4. How a prescription gets attached to the customer and bill

  1. Resolve the customer.

    Phone input becomes +919000000005. Source lookup returns a stable customer ID, name, phone and tags.

  2. Read the prescription list.

    The adapter asks the store-tool source for records matching the canonical phone. OperationsGateway merges these with locally authored clinical records using that phone. Lookup returns the list; it does not attach every record to a bill.

  3. Create a clinical record if needed.

    An optometrist submits a typed prescription body. The backend resolves the source customer and adds customer_id, rx_id, issue timestamp and the authenticated optometrist identity. It saves this record locally. It does not send it to Shopify or write it back to the store tool.

  4. Select during sale preparation.

    For every lens, the backend finds the latest issued prescription whose valid_until has not passed. It checks both eyes, lens limits and required ADD. Source records are trusted as supplied; independent customer-ID consistency checking on imported source Rx records is not added by this change.

  5. Persist on the lens line.

    The quote stores the chosen rx_id and wearer phone. The source order lens line properties include rx_id, wearer_phone and lens configuration. Frame/lens pair references link items within a wearer.

  6. Keep historical evidence stable.

    A new prescription does not rewrite a completed invoice or its source order. A remake links to the original sale and creates a new lens-only checkout with the appropriate current validation.

Canonical phone → current source/local Rx lookup
PrescriptionRecord.rx_id → saved quote lens line → source order line properties

Send to POST /api/prescriptions. od is right eye; os is left eye. Sphere, cylinder, axis and ADD are required for both eyes. Sphere, cylinder and ADD use quarter-diopter steps; axis is an integer from 5° to 180° in five-degree steps. Enter ADD as 0.00 when none is prescribed. The validity date must be today through two years ahead. The selected lens limits are checked again before the cart can be prepared.

Do not send customer_id or an approver identity to impersonate another record: the current clinical handler determines those from the resolved source customer and authenticated user. The schema accepts only the documented input fields; existing source prescription records may contain extra fields such as PD and notes.

6. Proposed new-customer registration — NOT IMPLEMENTED

Current lookup returning 404 should lead to a clearly designed registration workflow, not a silent local insert. This is the proposed design for a future ticket; neither the endpoint nor the source create operation below is active.

  1. Staff collects name, phone and any approved optional contact/consent fields.
  2. Normalize phone and validate fields before attempting a source write.
  3. Search for possible duplicates. A shared family phone is a business decision, not automatic proof of the same person.
  4. Create the customer through the approved external customer-creation adapter using a body, stable request key and a reviewed duplicate/uncertain-response strategy.
  5. Save/use the returned source customer ID. Do not report success when only a local record exists.
  6. Then an optometrist creates/attaches a prescription using the stable customer ID and their own identity.
  7. Only after that should lens billing proceed.

POST /sales/prepare — 3. Prepare a validated quote

Allowed roles: admin, cashier, manager

Reads customer, variants, billing location and stock from Shopify; staff and wearer prescriptions from SMT/local clinical records. A wearer can bill frame/lens pairs, ready-to-wear or prescription sunglasses, or lens-only pairs through lens_only_variant_ids. Every lens is validated against that wearer's prescription and carried on its Shopify line; standalone lens pairs have no frame pair_ref and do not affect frame inventory. Calculates effective-date HSN GST and discounts from local data. No coupon is applied unless selected_offer_id is supplied; then the server rechecks dates and cart/customer conditions and applies only that coupon. No manager discount is applied unless both override_bps and reason_code are provided with an authorized identity. Manager discount is exclusive of a coupon. Saves quote/order_payload in SQLite and reserves a store invoice number. Returns checkout_id. It does NOT charge payment, create a Shopify order or reserve physical inventory.

10. Internal storage and relationships

11. Verify and explain the change

  1. Restart the runner so the backend, wrapper and Swagger schema load the new contract. Do not recreate the virtual environment.
  2. Sign in, call POST /api/customers with {"phone":"9000000005"}. Confirm normalized phone and source customer ID.
  3. Repeat with +91, 91 and leading-0 formats. The same customer and Rx list should return.
  4. As optometrist, add a valid prescription using one format. As cashier, look up using another and prepare a lens bill. Verify chosen rx_id and wearer phone in saved quote/source payload.
  5. Inspect browser Network: lookup URL contains only /api/customers; phone is in Request Payload. Private source calls use /eluno/* body routes.
  6. Invalid/foreign number → 422; valid but unknown customer → 404; old GET customer route → 405; no session → 401; POST without CSRF → 403.
  7. Check access logs contain paths without phone-bearing queries. Do not assume proxy/APM/body logging is redacted without its own verification.
